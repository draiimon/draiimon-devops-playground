SLIDE 3: Part 3 CI/CD

SAY:
For Part 3, the local staging push handed work to GitHub Actions. The workflow order is Verify, Build, Test, Push, and Notify. Build validates the Compose configuration and images. Test installs dependencies, starts the real services, waits for readiness, and checks behavior. Only after those checks does the pipeline publish API and UI images to Docker Hub. SHA, staging, and latest tags make the output traceable.

SHOW / DO:
Trace the successful workflow graph from left to right and then show the published registry tag evidence. Open .github/workflows/deploy.yml if asked.

EVIDENCE NOTE:
The successful pipeline and registry publishing are captured evidence. Notification configuration is present, but I do not overclaim a new failure-notification capture or a live rollback test.

IF ASKED:
Fresh GitHub-hosted jobs do not share hidden local state, so each job checks out the code and declares its own setup. That makes the pipeline more reproducible.

SLIDE 4: Part 4 high availability

SAY:
For Part 4, I used a two-node Minikube cluster and raw Kubernetes manifests. The application has two API replicas and two UI replicas, stable Services, Ingress routing, readiness and liveness probes, HPA, a PodDisruptionBudget, rolling updates, and topology spread. I then used a runtime verifier instead of trusting YAML alone. The captured results show traffic reaching both replicas and 20 out of 20 successful HTTP responses while one node was NotReady.

SHOW / DO:
Show the ready pods, the 40-request distribution, and the controlled node-failure screenshot. Point out that preflight checks image consistency, EndpointSlice membership, routing, and /instance.

EVIDENCE NOTE:
This is the strongest HA boundary: the test exercises traffic and availability. The screenshots are local WSL captures; the Repl snapshot contains the verifier, manifests, documentation, and copied evidence.

IF ASKED:
Minikube is appropriate for a reproducible exam environment. In production I would repeat the same workload design in managed Kubernetes with stronger control-plane and observability guarantees.

SLIDE 5: Part 5 decisions and closing

SAY:
The main challenges were boundary problems: missing source in the first container build, database alignment, fresh CI runners, and a green rollout without traffic proof. I resolved them with source checks, MySQL alignment, explicit job setup, and runtime preflight. With more time, I would add image scanning, immutable digests, a tested rollback, and production observability. My main lesson is that reliable delivery is a chain of verified boundaries.
